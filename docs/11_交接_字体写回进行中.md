## 二、为什么改走"原地写回游戏资产"（原补丁的路子）

实测原补丁 `sharedassets0.assets` 与本体**对象数完全一致（193）**，只原位换了两样：
Gyate 字体 payload（730,248 → 212,484，2172 字形 → 口口口根因）、Gyate/Makinas 的 8192² 图集像素
（`.resS` 流式 → 内联，+134MB＝2×64MB）。
**因为 pathID / 材质 / 语言材质预设 / 图集↔材质配对全没动，所以描边、颜色、每语言材质天然正确**
——这就是"他很完善"的技术原因，也是运行时替换方案反复出问题的根因。

## 三、本轮拿到的格式事实（下次直接用，别再试错）

* **UnityFS 头**：`"UnityFS\0"` + u32 版本 + **两个** null 结尾字符串（unityVersion、unityRevision）
  + i64 size + u32 compressedBlocksInfo + u32 uncompressedBlocksInfo + u32 flags
* **目录信息(blocksInfo) 仍会被 LZ4HC 压缩**（实测 91→65 字节），即使 `UncompressedAssetBundle`；
  数据块才是未压缩的（块 flags `&0x3F == 0`）。需自己实现 LZ4 块解压（已在 `bundle_extract.py`）。
* **目录信息布局**（实测）：`[16 字节保留] u32 block_count + 每块(u32 uSize,u32 cSize,u16 flags) + u32 node_count + nodes`
* **SerializedFile 头是大端**：metadataSize / fileSize / version / dataOffset（本例 345 / 67,799,160 / 19 / **4096**）,
  然后 endianFlag(1) + 3 字节补齐 + cstr(unityVersion) + i32(targetPlatform) + bool(enableTypeTree)
* ★**元数据段（类型表/对象表）是小端**★ —— 我在新脚本里一律用 `>` 解析，因此连续失败多次；
  证据：dump 里 `8e 00 00 00` 就是 AssetBundle classID 142 的小端写法
* **对象条目 = 20 字节**（v19）：`i64 pathID, u32 byteStart, u32 byteSize, i32 typeID`（我一度写成 24，错）
* 抽出的 SerializedFile 长度与头的 `fileSize` **分毫不差**（67,799,160 ✓）
* **按内容定位对象**（最稳，绕开对象表）：Unity 字符串 = `[i32 len][bytes][pad]`；
  MonoBehaviour 的名字在 payload+28，Texture2D/Material/Shader 的名字在 payload+4。已实测：
  - 图集对象 = `[688456, 688456+67,108,984)`（名字 `KotonohaCreator Atlas` @688460，前缀 21 ✓）
  - 字体资产 `m_Name` @15072（前缀 15 ✓）→ payload 起点 ≈ **15040**
  - Shader 对象 ≈ `@4096` 起，其属性表列全了 TMP 材质属性名
    （`_FaceColor/_FaceDilate/_OutlineWidth/_Underline…/_GradientScale/_ClipRect/_Stencil*`）
