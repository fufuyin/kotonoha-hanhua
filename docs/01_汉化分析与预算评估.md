## 三、技术架构（实测链路）

### 3.1 文本加载链（已从反编译源码确认）

```
DataListManager.loadDataList()
  └─ ResourceManager.getTextDataList()
       └─ Resources.LoadAll("dataList/TextData", typeof(TextData))   // 489 个 ScriptableObject：id / type / pass
NobelManager.startNobel(ETextType.xxx)
  └─ ResourceManager.getTextData(type)
       └─ Resources.Load("Text/" + textData.pass) as TextAsset      // ← 真正的剧本文本
            → (Resources.Load(...) as TextAsset).text
```

* 反编译证据：`ResourceManager.cs:244-255`、`DataListManager.cs:604`、`TextData.cs`
* `ETextType.cs` 共 **489** 个枚举项，与实测 **489 个 TextAsset** 数量完全吻合 → **文本无遗漏、无硬编码残留**

### 3.2 剧本文件格式（自定义标记语言）

```
<movelock>

<move><controller><0><-1><left><false>

<action><controller><sit>

<wait><1.5>

<main><japan><3><akane><1><right>
<あ～～～>

<main><japan><0><aoi_1><2><left>
<お姉ちゃんが商店街の福引で

特賞の「南の島旅行」を当てて>
```

* **命令行**：全 ASCII 标签，如 `<main> <japan> <akane> <left> <right> <flag> <if> <end> <imageOpen> <wait>`
* **台词载荷**：`<` 与 `>` 之间的日文，可为多行；空行 = 分页/等待
* 实测命令标签 **1,060 种**，`<main>` 出现 **7,904 次**
* 说话人 / 语言 / 表情 / 站位均编码在命令行中 → **翻译上下文充足**，质量可控

## 五、技术路线建议

### 路线 A：纯资产改写（不碰代码）
1. 解析 `resources.assets` → 提取 489 个 TextAsset
2. 翻译后**重建序列化文件**（重算所有对象偏移，工具已具备解析能力）
3. 字体：重建 8192² SDF 图集 + 字形表，或原地替换内嵌 Font 数据 + 把 `m_AtlasPopulationMode` 由静态(0)改为动态(1)
4. 优点：逻辑零改动，理论最安全；缺点：字体重建是重工程，失败点集中且难回退

### 路线 B：代码补丁 + 外置译文表（**推荐**）
1. 用反编译源码，仅改动 `ResourceManager.getTextData()` 一处：命中译文表则返回中文，否则回落原文
2. 译文表外置为 `kotonoha_Data/translation/*.json`（不进 assets，便于增量更新与校对）
3. 字体：启动时 `Font.CreateDynamicFontFromOSFont("Microsoft YaHei"/"SimHei", …)` + `TMP_FontAsset.CreateFontAsset()`，把生成的中文字体资产加入各 TMP 字体的 **fallbackFontAssetTable** → **完全绕开静态图集重建**
4. UI/系统文本同理走运行时替换
5. 优点：不动 36 MB 资源、字体问题被彻底规避、迭代成本极低、可做语言切换开关
6. 风险：需重新编译 `Assembly-CSharp.dll`（502 文件）；须先验证"仅重编译、不改逻辑"的 DLL 能让游戏正常启动

### 推荐执行顺序
```
① 原生 DLL 重编译冒烟测试（不改逻辑，验证能进标题画面）——决定路线上限
② 文本提取 → 分段 → 术语表 → 试译 1 章 → 注入 → 实机验证排版/字体
③ 全量翻译（分批 + 缓存 + 术语一致性）
④ 图片文字核对与修图
⑤ 打包补丁（备份/还原脚本 + 安装说明）
```

## 七、预算评估（DeepSeek-V4-Flash，推理等级 High）

### 7.1 计费单价（官方定价页实测，2026）

| 项目 | 空闲时段 | 高峰时段 |
|---|---|---|
| 输入（缓存未命中） | **$0.15 / M** | $0.30 / M |
| 输入（缓存命中） | **$0.003 / M** | $0.006 / M |
| 输出（含思考 token） | **$0.60 / M** | $1.20 / M |

* 高峰 = 周一至周五 UTC 01:00–04:00 与 06:00–10:00 → **北京时间 09:00–12:00、14:00–18:00**；其余（含北京 18:00–次日 09:00、12:00–14:00）为空闲，**半价**
* **推理等级 High 的思考 token 按输出计费**，是成本主导项

### 7.2 估算模型

* 输入侧：日文 ≈ **1 token/字符**（保守）
* 输出侧：中文译文 ≈ 1 token/字符；思考 token 按策略取值
* 术语表 + 规则提示词固定置于请求首部 → 命中缓存（成本降 50–100 倍）

### 7.3 三种策略费用（按 16.1 万字计）

| 策略 | 请求数 | 输入 token | 输出 token | 空闲时段费用 | 高峰费用 |
|---|---|---|---|---|---|
| **S1 批量直译**（25 段/请求，单遍，High 思考 ~3k/请求） | ~416 | 1.14 M | 1.54 M | **≈ $0.97** | ≈ $1.94 |
| **S2 逐段+上下文**（12,000 请求，High 思考 ~0.6k/请求） | ~12,000 | 27.6 M | 7.8 M | **≈ $5.3** | ≈ $10.6 |
| **S3 生产级**（S2 + 审校轮 + 30% 重译 + 术语校验） | ~26,000 | 51 M | 14 M | **≈ $9.4** | ≈ $18.8 |
| **S4 重度冗余**（多轮全量重译 + 高思考 5k/请求 + 高峰运行） | ~40,000 | 90 M | 55 M | — | **≈ $90** |

> 人民币折算（≈7.1）：S1 ≈ 7 元；S2 ≈ 38 元；S3 ≈ 67 元；S4 ≈ 640 元。

### 7.4 结论与建议额度

* **正常预期**：采用 S3 生产级流程、空闲时段运行 → **$6–12（40–85 元）**
* **含反复迭代与返工**：**$15–30（105–215 元）**
* **建议充值上限**：**$50（≈360 元）**，可覆盖 2–3 倍返工余量
* 若由 DSH 智能体驱动全流程（编排/校验/试跑），额外编排开销按 1.5–2× 计，仍**不超过 $100**

### 7.5 省钱要点

1. **术语表与系统提示固定前置** → 命中缓存，输入成本降到 1/50
2. **推理等级：批量翻译用 Low/Off，仅审校与难点用 High** → 可再省 3–5 倍（High 的思考 token 是主要开销）
3. **避开高峰时段**（北京 09–12、14–18）→ 直接半价
4. **批处理**（20–30 段/请求）而非逐字逐句
5. **译文表外置**，返工只重跑变更段，不重跑全量
