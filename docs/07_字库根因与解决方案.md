# 07 字库问题的根因与解决方案（重烤字体资产 + 运行时替换）

## 一、根因（本轮查清，全部有程序化证据）

### 1. 字为什么"缺失"：旧补丁的字体只有 2172 个字形
- 游戏有 5 个 TMP 字体资产（`resources.assets` 1 个 + `sharedassets0.assets` 4 个）：
  | 字体资产 | 所在文件 | 图集 |
  |---|---|---|
  | GDhwGoJA-OTF112b2 | resources.assets | 8192×8192 Alpha8（**流式**，数据在 resources.assets.resS）|
  | Makinas-4-Square | sharedassets0.assets | 8192×8192 Alpha8（内嵌）|
  | Gyate-Luminescence | sharedassets0.assets | 8192×8192 Alpha8（内嵌）|
  | Stick_Regular | sharedassets0.assets | 4096×4096 Alpha8（内嵌）|
  | RiiPopkkR | sharedassets0.assets | 4096×4096 Alpha8（内嵌）|
- 其中被上一版汉化换成的中文字体只覆盖 CJK 区约 2172 个码位，且完全没有 ASCII / 全角标点
  → 超出部分与标点全部变成豆腐块（用户看到的"文字缺失"）。

### 2. Unity 侧"烤不出来"的真正原因（不是缺字形）
用官方 Font Asset Creator 的代码路径逐码位测试后确认：

| 现象 | 证据 |
|---|---|
| 74 个码位（U+00AE–BD、U+2014–2049、U+2190–21D4、U+2200–226A 等）用 `TMP_FontAsset.TryAddCharacters` 永远加不进去 | 每次调用抛 `NullReferenceException`，`characterTable` 计数 0→0 |
| 这些码位**字体里确实有**，且能画出来 | OTF cmap 全都有；GDI+ 独立渲染 74/74 有墨；`FontEngine.TryGetGlyphIndex` 全部 True |
| 换 glyf TTF（NotoSansSC-VF.ttf）也一样失败 | 说明与 CFF/glyf 无关，是 TMP 内部 API 的问题 |
| **官方 Font Asset Creator 路径完全正常** | `TryGetGlyphIndex` + `TryGetGlyphWithIndexValue(LOAD_RENDER|LOAD_NO_HINTING)` + `TryPackGlyphsInAtlas` + `RenderGlyphsToTexture`：74/74 有非零字形矩形；整charset 烘焙 7895/8745 成功（含全部关键标点 …… —— “ ” · ° ℃） |

结论：**必须用 Creator 路径烘焙**。而 `TryPackGlyphsInAtlas` / `RenderGlyphsToTexture` /
`TryAddGlyphToTexture` 在 `UnityEngine.TextCore.LowLevel.FontEngine` 上是 **internal**
（TMP 自己靠 InternalsVisibleTo 调用），普通 Editor 脚本只能用反射调用。

### 3. 本次烘焙产物
- 工程：`F:\Application\Unity`（Unity 2019.1.13f1，与游戏同版本）
- 脚本：`Assets/Editor/FontCreator.cs`（Creator 路径 + 反射调用 internal API）
- 源字体：`Assets/Fonts/NotoSansCJKsc-Regular.otf`（OFL）
- 字符集：`F:\Application\Unity\charset.txt` = 补丁译文 ∪ 场景/UI 字符串 ∪ DLL #US 字符串 ∪ 固定标点
  = **8745 码位**（由 `_hanhua/tools/make_bake_charset.py` 生成）
- 产物：`Assets/BakedFonts/KotonohaCreator.asset` — 8192×8192 Alpha8 图集、**7897 字符 / 7892 字形 / 7890 有像素**
- 验收：`_hanhua/tools/verify_bake.py` →
  补丁译文需要 2135 个码位，**缺 0**；全量需要 7639，缺 23（其中 20 个是 raw 字节扫描噪声、
  1 个 U+200F 类不可见控制符、U+0020/U+3000 是空格本来就无墨，**真实文本无缺字**）
- 打包：`_hanhua/tools/BundleBuilder.cs.staged` → `kotonoha_font.bundle` 17.4 MB（LZ4）

## 二、交付路线

### 路线 A（当前验证中）：BepInEx 插件运行时替换字体
- 插件源码 `_hanhua/plugin/KotonohaCNFontV2.cs`，编译 `_hanhua/tools/build_plugin.ps1`
- 原理：AssetBundle 里带完整 TMP_FontAsset（自带图集+材质+shader），插件把每个
  `TMP_Text.font` 指过去。TMP 的 `font` setter 会调 `LoadFontAsset()`，其中
  `m_sharedMaterial = fontAsset.material`（TMPro_UGUI_Private.cs:534），所以图集与材质一致，
  不会再出现 v1.3 那种"跨图集→乱码"。
- 优点：不动游戏文件、可整体卸载、单张图集省内存
- 缺点：依赖 BepInEx（已在游戏目录部署好）

### 路线 B（后续，纯文件补丁）：直接改写 SerializedFile
- 关键事实：字体图集 4 个内嵌、1 个流式（.resS）；4 个字体资产在**同一个文件**（sharedassets0.assets）
- 做法：把新字体资产/图集的 payload 追加到文件末尾，只改对象表里对应条目的
  `byteStart/byteSize`（pathID 不变 → 所有引用自动指向新数据），并同步 `.resS` 偏移。
  比"整体重建 SerializedFile"风险低得多。
- 需要的额外工作：TMP 字体资产 player 版序列化布局（字段顺序 = TMP 源码声明顺序去掉
  `#if UNITY_EDITOR` 字段，基类 TMP_Asset 的 `hashCode/material/materialHashCode` 在前），
  可用 bundle 里的 player 版实例做校验基准。
