# 路线修订：全量重编译方案的可行性结论（否决）

> 结论：**放弃"反编译 → 改代码 → 全量重编译 Assembly-CSharp.dll"方案**。有实测证据，见下。

---

## 一、验证过程（可复现）

| 步骤 | 命令/工具 | 结果 |
|---|---|---|
| 反编译 | `dnSpy.Console.exe`（本机已装，v6.1.5） | 501 个 `.cs`，3.7 MB，全部类可见 |
| 编译器选型 | 本机 `dotnet` **无 SDK**；无 `mcs.exe`；Windows 自带 `csc.exe` 仅 C# 5 | 改用 **dnSpy 内置 Roslyn 2.10**（`Microsoft.CodeAnalysis.CSharp.dll`），在 **PowerShell 5.1** 中加载成功 |
| 引用集 | `kotonoha_Data\Managed` 下 91 个程序集 | 引用解析正常 |
| 首轮编译 | `_hanhua/tools/build_dll.ps1` | **3,423 errors / 46,471 warnings** |
| 自动语法修复 | `_hanhua/tools/fix_decomp.py`（449 处编译器生成标识符） | **1,806 errors** |

## 二、残余错误分类（全部源于 dnSpy 输出缺陷）

| 错误码 | 数量 | 根因 | 可自动修复性 |
|---|---|---|---|
| CS1061 | 528 | 成员"不存在"（如 `BattlePlayerController.keyManager`）——类结构被提前闭合导致字段落到类外 | 需先解决结构错位 |
| CS1056/CS1002/CS1003 | 560 | `CS$<>8__locals1` 这类**含 `$` 的编译器生成局部变量名** | 可正则修复 |
| CS0104 | 189 | `Object` 在 `UnityEngine.Object` 与 `object` 间歧义 | 可加 `using Object = UnityEngine.Object;` |
| CS0116 | 67 | "命名空间不能直接包含成员"——**类括号结构错位** | 仅 5 个文件括号不平衡，需人工核对 |
| CS0122 | 45 | 成员因 `CS0116` 的 `<invalid-global-code>` 上下文而不可访问 | 随 CS0116 消失 |
| CS0165 | 43 | `Action __9__1;` 未初始化即使用 | 可正则修复 |
| CS0012 | 25 | 需 `netstandard.dll` 引用（我首轮主动排除了它） | 可修复 |
| CS0030 | 19 | **`Cannot convert type 'System.Object' to 'BGMData'`** —— dnSpy 把方法返回类型推断错了，生成的代码**并不忠实于原始 IL** | 需逐点人工修复 |
| CS0103 | 63+ | `fieldof(...)` 是 dnSpy 的**伪表达式**（映射自 `InitializeArray` + `<PrivateImplementationDetails>` 数据块），不是合法 C# | 需数据块改写 |
| 其他语法类 | ~200 | `base..ctor()`（3 处，构造函数体内的基类调用，C# 非法）等 | 需逐点修复 |

## 三、否决理由

1. **不是环境问题，是反编译产物的固有失真**。`CS0030` 证明 dnSpy 生成的源码在语义上已偏离原始 IL；即使把 501 个文件全部修到"能编译"，也**无法保证行为等价**。
2. **风险与收益严重不匹配**。本项目只需替换文本；为文本而重做 500 个类的实现，一旦出现细微行为差异（存档、战斗状态、Steam 初始化），将表现为难以定位的游戏 bug。
3. **工作量不可控**。1,806 个错误涉及 10 类根因，其中结构错位与语义失真需逐文件人工核对；且每轮验证都要完整编译 + 实机启动。
4. **无编译器红利**：本机无 .NET SDK / mcs，只能用 dnSpy 附带的 Roslyn 2.10（C# 7.3），进一步限制修复空间。

## 四、修订后的推荐路线（纯资产路线，无需改代码）

| 模块 | 方案 | 状态 |
|---|---|---|
| **文本** | 解析并回写 `resources.assets` 内 489 个 TextAsset | ✅ 解析器已验证；回写机制待实现 |
| **字体（首选）** | ① 把内嵌 Font 资产（如 `GDhwGoJA-OTF112b2`）的字体数据替换为**用户本机系统中文字体**（安装时提取，不随补丁分发）② 把 TMP 字体资产的 `m_AtlasPopulationMode` 由静态(0)改为动态(1) ③ 补写 `m_SourceFontFile` 指向该 Font 资产 ④ 把图集贴图 `m_IsReadable` 改为 true | ⚠️ 四处均为定长字段原地写入，需实机验证 TMP 动态补字是否生效 |
| **字体（备选/最稳）** | 自建 SDF 图集：为译文字符集生成 SDF，打包进 8192² Alpha8 图集 + 重写字体资产的 glyph/character 表（保留原日文字形以兼容残留日文） | 工作量大但完全确定性，无运行时不确定性 |
| **图片** | 一期不做（按你的决定） | — |

## 五、实测到的关键前提（影响字体方案）

| 事实 | 值 | 影响 |
|---|---|---|
| TMP 主字体资产 | `GDhwGoJA-OTF112b2 SDF`，对象 729,416 B | 含完整字形/字符表（静态烘焙） |
| 图集贴图 | `GDhwGoJA-OTF112b2 SDF Atlas`，**8192×8192 Alpha8** | 容量大，但已被日文字形占用 |
| 字体资产是否引用源字体 | **未引用**（`Font` 资产 pathID `0x2ba4` 在其 729KB 数据中 0 次出现）→ 构建时已剥离 | TMP 动态补字的**源字体缺失**，必须补写 PPtr |
| 图集贴图 `m_IsReadable` | **False** | 动态补字无法写入，必须改为 True |
| 内嵌 Font 资产 | 5 个，共约 13.4 MB（GD-HighwayGothicJA-OTF 880 KB 等） | 字体数据可原地替换（保留声明长度、尾部补零） |

## 六、附带发现的一条环境坑

PowerShell 5.1 读取**无 BOM 的 UTF-8** 脚本文件时按 ANSI 解码，中文注释会变成乱码字符并**破坏脚本语法**。所有 `.ps1` 必须纯 ASCII，或存为带 BOM 的 UTF-8。
