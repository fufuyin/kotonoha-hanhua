## 2. 诊断阶段：问题到底出在哪

| 结论 | 证据 |
|---|---|
| 口口口的根因 = **补丁只替换了 Gyate 一个字体资产** | 原版 730,248B / 6985 字形 → 补丁 **212,484B / 2172 字形**；其余 3 个字体字节数完全未变 |
| 补丁文件膨胀 36,490,412 → 170,190,332 B 的原因 = 工具把 2 张 8192² 图集**改为内联** | 图集对象 payload 67,108,988 B |
| 补丁作者**只改过 1 个材质数值** | 逐属性 diff：`Gyate-Luminescence SDF Material (0x1a)` 的 `_OutlineWidth` `0.0 → 0.3`（白描边）|
| 游戏实际使用 **5 个字体** | 运行时日志：Gyate / Makinas-4-Square / RiiPopkkR / Stick_Regular / GDhwGoJA-OTF112b2 |
| 字体观感差异 = 补丁用**黑体 SimHei**，而我方初版用圆体 | 度量剖面匹配（见 §4.4）|
| 行距过宽 = 我方初版 FaceInfo 采信了**源字体**的 1.448 em 行高 | 补丁 FaceInfo `lineHeight/pointSize = 1.000`；我方初版 `81.088/56 = 1.448` |

## 3. 技术路线（最终采用的）

**资产级拼接（不依赖插件也能修主字体）**

```
自烤 TMP 字体资产 + 图集像素
        │  （Unity 2019.1.13f1 批处理：FontBakerTwo.Bake → BundleBuilder.Build）
        ▼
以原补丁的 sharedassets0.assets 为输入
        │  splice_fonts.py：把字体 payload 追加到文件尾、改对象表；图集像素原地覆盖
        ▼
产出 .test 文件 → verify_splice.py 独立校验 → install_assetfix.ps1 安装（自动备份）
```

**关键设计原则**：只替换「字体 payload + 图集像素」两处，**材质的 PPtr 与材质↔图集配对一律不动**——
这样描边、颜色、每场景样式全部沿用原补丁（这也是原补丁描边正确的原因）。
字体资产的名字、`m_Script`、`m_Enabled`、尾部权重表都照抄目标文件，避免任何悬空引用。

**字体烘焙配方**（`F:\Application\Unity`）
* 主字体：`Assets/Fonts/simhei.ttf`（黑体）→ 补字：`Assets/Fonts/NotoSansCJKsc-Regular.otf`
* `pointSize=56`、`padding=10`、`atlas=8192²`、`_GradientScale=11`、字符集 `charset.txt`
* 输出：`Assets/BakedFonts/KotonohaCreator.asset` + `twobake_atlas.bin`（后者是校验用的"黄金像素"）

## 4. 关键技术真值（都从实证反推，不是猜的）

### 4.1 容器格式
* SerializedFile **v19**：头部 4 个 u32 是**大端**，元数据段是**小端**；对象条目 **20 字节**；`绝对偏移 = byteStart + dataOffset`。
* UnityFS (v6)：头里是**两个** null 结尾字符串；`flags & 0x3F` 是目录信息(blocksInfo)的压缩方式，数据块各带自己的 flags；目录信息布局 `[16B 保留] u32 块数 + 每块(uSize,cSize,flags) + u32 节点数 + 节点`。
* **坑**：自家 bundle 内嵌 SerializedFile 的版本串不以 4 字节对齐结束（`2019.1.13f1\n2`，13 字节）→ 盲目 `align(4)` 会让整个元数据段错位 2 字节、解析跑到文件尾。修法：候选起点两处都试，用"对象表全落在文件内"判定。

### 4.2 Texture2D 像素锚点
payload 里值是 `8192×8192` 的 i32 **不止一个**（`m_CompleteImageSize` 也等于它）。
**真锚点判据**：取**最后一个**匹配，且其后恰好 12 字节全零（`m_StreamData` 的 offset/size 为 0）、前 4 字节为零。
实测：我方资产 `+104`、补丁图集 `+108`（差值 4 = 资产名长度差）。
*校验方式*：拿外部"黄金像素" `twobake_atlas.bin` 直接比对，一致才算锚点正确。

### 4.3 TMP_FontAsset 序列化布局（逐字段实测）
```
+0   m_GameObject PPtr(12)      +12  m_Enabled u8=1 + 3 填充
+16  m_Script PPtr(12)          +28  m_Name 字符串
     TMP_Asset: hashCode(i32) / material(PPtr12) / materialHashCode(i32)
     TMP_FontAsset: m_Version("1.1.0") / m_SourceFontFileGUID(32字符) / ...
尾部 [-272: i32 count=10][-268:-28: m_FontWeightTable 240B][-28:-16: null PPtr][-16: 样式4值]
```
* **重要**：原版 **Makinas / GDhwGoJA 的尾部比我们多 4 字节**（count 在 `-268`）→ 说明它们的字段集与我们不完全同构，
  **不能盲目把我们的 payload 替换给它们**（会字段错位）。本次替换的 Gyate 与补丁版同构，已实测可用。
* 我们的工程资产把 `m_FontWeightTable` 全填成"指向自己"→ 直接搬过去就是**悬空引用**，
  修法：**固定字段一律照抄目标文件**。

### 4.4 字体识别：靠度量剖面，不靠看图
补丁字体 FaceInfo `ascent=146.0938/170=0.85938`、`descent=-23.9062/170=0.14063`
= `220/256`、`36/256` → 源字体 `unitsPerEM=256, hhea=(220,-36)`。扫本机字体：

| 字体 | upem | ascent/em | descent/em | 距离 |
|---|---|---|---|---|
| **C:\Windows\Fonts\simhei.ttf（黑体）** | **256** | **0.85938** | **0.14062** | **0.0228** |
| LXGWWenKai（霞鹜文楷）| 1000 | 0.92800 | 0.25600 | 0.2143 |
| NotoSansSC | 1000 | 1.00000 | 0.20000 | 0.2683 |
| 微软雅黑 | 2048 | 1.05811 | 0.26172 | 0.4115 |
| ChillRoundGothic（初版用的）| 1000 | 1.16000 | 0.28800 | 0.5163 |

### 4.5 TMP 材质口径公式（从原版 4 组数据反推，逐条验证）
* `_GradientScale = padding + 1`（padding 10 → 11；Rii/Stick 是 padding 5 → 6）
* `_ScaleRatioA = 1 − 1/_GradientScale`（10 → 0.909091；5 → 0.833333）
* `_ScaleRatioB = _ScaleRatioC = _ScaleRatioA × (0.8125 − _FaceDilate)`
  （验证：×0.8125=0.738636 ✓ ×0.6125=0.556818 ✓ ×0.5625=0.511364 ✓ ×0.6625=0.602273 ✓）
* 描边实际宽度 = `_OutlineWidth × _ScaleRatioA` → **这几个系数是几何口径，不是风格值，必须与图集 padding 一致**。

### 4.6 烘焙脚本的两个坑
1. **FaceInfo 取的是"最后加载的字面"**（= 补字字体），不是主字体 → 烤完必须再套一次
   `patch_faceinfo.py` 把 FaceInfo 校正到补丁比例，否则行距回到 1.16~1.448 em。
2. **Unity 启动器会提前返回**：`& Unity.exe` 立刻返回而编辑器仍在跑；
   且工程若需全量重编译，第一次 `-batchmode -quit -executeMethod` 只编译不执行方法，**要跑第二遍**。

## 9. 经验教训（已固化成 SOP）

1. **真值优先**：动手前先拿地面真值——① 原版未改文件 ② 包源码（TMP_FontAsset.cs 字段顺序）③ 外部黄金产物（`twobake_atlas.bin`）。
2. **探针先行，变异在后**：新字段先写探针打印解码结果并断言，通过才写修改代码。
3. **判据要量化命中率**：任何自动修正的触发条件，先在真实数据/日志上量命中率
   （教训：`preferredWidth > 方框宽度` 实测 **0/30** 命中，改用 `textInfo.lineCount`）。
4. **不盲替**：布局不完全同构的资产不能直接搬 payload（Makinas/GDhwGoJA 尾部差 4 字节）。
5. **固定字段照抄目标**：权重表这类固定结构沿用目标原值，避免悬空引用。
6. **交付前干跑**：安装 → 逐文件哈希核对 → 回滚 → 原文件哈希还原 + 新增文件清除。
   （这一步抓到了回滚"多退一层目录"和"把 rollback.ps1 复制进游戏根"两个真 bug。）
7. **小步快跑、每步一验**：一次只改一处，改完立刻独立校验，通过再下一步。
8. **一次性只动必要对象**：其余对象逐字节不变，才能把风险限制在可控范围。
